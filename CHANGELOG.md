# Changelog

## Unreleased

### Features

- [Monorepo] **Work on one application at a time**: each module has an *Active* box, and the tool window's module selector lists the modules set aside and offers *Focus on This Module* and *Activate All Modules* (also under *Tools › i18n Support Plus*), with *Undo*
- [next-intl] **`t.rich`, `t.markup`, `t.raw` and `t.has` are read**: their keys are checked, completed, folded and navigable like `t('key')`; `t.raw` may point at an object, and `t.has` is never reported missing
- [svelte-i18n] **`$t`, `$format`, `$json` and `$_({ id })` are read**: the aliases of `$_` and the descriptor form are checked, completed and navigable like `$_('key')`, and `$json('nav')` may point at an object
- [Laravel] **Values folded and shown as inlay hints, keys renamed in the PHP arrays**: `__()`, `trans()`, `trans_choice()`, the translator and Blade's `@lang`, `@choice` and `{{ __() }}` show their value in place; Shift+F6 renames the key in `lang/<locale>/<file>.php` of every locale as well as its calls
- [React Intl] **Navigate, rename and extract with react-intl's own calls**: Ctrl+click, Find Usages and Shift+F6 work on the ids of `<FormattedMessage>`, `formatMessage` and `defineMessages`; *Extract I18n* writes `<FormattedMessage id="…" />` or `intl.formatMessage(…)` and adds the import, and *Internationalize…* gives a component its `useIntl()`
- [vue-i18n] **`useI18n()` under the vue-i18n preset, and plural branches checked**: `t('…')` and `te('…')` taken from `useI18n()` are read in the script and the template; the *vue-i18n plural branches* inspection reports a plural `a | b` with fewer branches than the language needs (`ru`: `one`, `few`, `many`)
- [Review] **Suggestions and replies in review threads**: a change request can carry a suggested value, applied in one click with *Apply suggestion*, and each entry can be replied to and resolved
- [Settings] **Locale aliases**: a folder named with a country code (`gb/`, `jp/`) is read as the locale you map it to (`gb=en-GB`) instead of being left out
- [Settings] **Import key assistance rules from i18n Ally**: *Import from i18n Ally…*, under the rules, reads `.vscode/i18n-ally-custom-framework.yml` and shows what it takes over before adding anything
- [CLI] **`i18n-check`, the translation check for CI**: reports missing, orphan and empty keys per locale and, with `--code`, the keys an i18next project no longer uses. It reads the IDE's settings or an `i18n-check.json`, and JSON, JSON5, YAML and TS/JS catalogues; it is attached to each GitHub release and runs as a GitHub Action. See the [README](README.md#command-line-check)

### Fixes

- [Monorepo] **Each application's keys are checked against its own files** ([#620](https://github.com/IBRAHIMDANS/i18nSupportPlus/issues/620)): the setup wizard now roots a module at its application (the folder of its `package.json` or `composer.json`) and gives it its framework; usages, unused keys, *Cleanup Unused Keys* and *Sync Keys* work per module; an attached project with no module is no longer read. Modules already configured are not changed: set their root directory to the application's folder
- [Settings] **Ignored locales are ignored everywhere** ([#620](https://github.com/IBRAHIMDANS/i18nSupportPlus/issues/620)): the gutter, *Create missing keys*, the plural forms inspection, *Sync Keys* and the AI agents' tools no longer ask for a locale listed in *Locales not checked for missing keys*
- [Settings] ***First component as namespace* works again**: with it ticked, `t('common.title')` is looked up in the `common` file
- [Settings] **A project stored under a folder named `build`, `dist` or `node_modules` finds its translation files again**
- [Review] **A nested plural form (`steps.few`) turns stale when its `other` form changes**, as a flat `item_few` does
- [Lingui] **`<Trans>Hello {name}!</Trans>` is found in the catalogue again**: its key is built the way Lingui's macro builds it
- [React Intl] ***Internationalize…* leaves out a string outside any component** instead of calling an `intl` that is not there
- [Translation] **The translation dialog's *Translate* button and *Instruction* field are translated into French**
- [svelte-i18n] **The `default` and `values` of a `$_` call are no longer reported as unresolved keys**
- [Laravel] **A JSON phrase holding `.` or `:` resolves**: `__('Saved.')` and `__('Hello, :name')` are looked up whole in `lang/<locale>.json`, as Laravel does, instead of being cut at the separators
- [Gutter] **No more error logged for a key in a Vue template** (*LineMarker is supposed to be registered for leaf elements only*)

### Documentation

- [Examples] **Eight example projects to try the plugin on**, in `examples/`: vue-i18n, next-intl, svelte-i18n, Laravel, Angular (Transloco and ngx-translate), react-intl, Lingui and a four-application React monorepo, each listing the cases to check
- [Docs] **README and [comparison page](docs/COMPARISON.md) up to date**: supported languages and file formats, and the comparison with i18n Ally, Easy I18n and the others re-checked on 2026-10-25

## 1.15.0 - 2026-10-18

### Features

- [Paraglide] **`m.hello()` in Astro components is covered**: with the Astro plugin installed, a message called in the `---` frontmatter or in a `{…}` template expression — `import { m }` or Paraglide 1's `import * as m` — is resolved, an unknown one is underlined as *Unresolved key*, completion after `m.` offers the messages, and Ctrl+click on a message in a message file reaches its call sites in the component. It already worked; it is now tested, and the README no longer says Astro components are untested
- [Inspections] **A key absent from the reference locale is reported** (*Translation key absent from the reference locale*, disabled by default): `user.nmae` in `fr/common.json`, which `en/common.json` does not hold — a key renamed in the reference only, or a typo — is underlined on its name. Quick fixes remove it from the locale or add it, empty, to the reference locale. Plural forms are compared as a group, so `ru`'s `item_few` is not reported when `en` has `item_one` / `item_other`; the reference file and ignored locales are never reported
- [Stats] **The *Stats* tab counts the translations left to review**: in a module with a `.i18n-reviews/` folder, hovering a locale cell tells how many of its keys are to review, and how many of them were decided on a source text changed since: the keys the table's *To review* and *Source changed* filters list for that locale. Nothing changes in a project without reviews
- [Settings] **A natural key order**: *Key order* offers *Natural*, which ignores case and compares numbers by value, so `item2` comes before `item10` — the other orders put `item10` first. *Sort i18n Keys* and the keys inserted in order both follow it. Equal numbers with leading zeros come after the shorter ones (`a1`, `a01`). See the [README](README.md#key-extraction)

### Fixes

- [Review] **A comment of a review thread keeps the fields a later version of the plugin wrote on it**: when a colleague on a newer version adds a field to an entry of a review thread in `.i18n-reviews/<locale>.json`, rewriting the file from this version kept the entry but dropped that field. It is now written back as it was read, as the unknown fields of a review already were
- [Reviews] **A plural form the reference locale lacks turns stale when the reference's `other` form changes**: Russian `item_few` and `item_many` are translated from English `item_other`, and are now compared with it. They had no source at all, so their approval held whatever the English text became. The table, the key dialog, the *Stale translation* inspection and *Retranslate Stale Translations* read the same source. *Fill Missing Translations* and *Translate* record it for a form translated from `other`. A review recorded without a source is not flagged

## 1.13.0 - 2026-10-16

### Features

- [Paraglide] **Paraglide JS support**: `m.hello()` and `m["user.profile.title"]()` are read as keys in a file importing Paraglide's message object (`{ m }`, `{ m as msg }` or `import * as m`), in `.js`, `.ts` and Svelte components. See the [README](README.md#supported-frameworks) and [examples/paraglide-js](examples/paraglide-js/README.md)
  - The setup wizard detects `@inlang/paraglide-js` and its adapters, and the message files are found where `project.inlang/settings.json` puts them, monorepos included
  - An unknown message is underlined, one missing in a locale is reported, and the generated code is never counted as a use
  - Completion after `m.` offers every message with its value, including the ones not compiled yet
  - `m.hello()` folds into its message, and hover and inlay hints show it; a message with variants shows its catch-all branch
  - Ctrl+click opens the message rather than the generated JavaScript, and Shift+F6 renames it in every locale and at every call site
  - *Extract I18n* writes `m.save_changes()` and adds the import when the file lacks it
- [Reviews] **Translations whose source changed since they were reviewed are flagged and can be retranslated**: where a module keeps reviews (`.i18n-reviews/`), a value approved before its reference text changed reads *To review (source changed since the decision)* in the table and the key dialog, and is underlined by a new inspection. *Retranslate Stale Translations…* (Tools menu, or a locale column of the table) translates them again in one go, with a preview and one Ctrl+Z
- [Translation changes] **Retranslate the locales left behind by a change of the reference, with or without reviews**: *Show Translation Changes* and *Compare Translations with Branch…* offer *Retranslate Lagging…* on the locales that did not follow, and let you pick the reference locale when modules translate from different ones
- [MCP] **AI agents can list and retranslate the translations whose source changed**: a new tool, `i18n_stale_translations`, and `i18n_write_translations` may now replace such a value
- [Inspections] **Key naming convention** (off by default): a key that does not follow camelCase, snake_case, kebab-case or a pattern of your own is underlined, and *Rename to '…'…* renames it everywhere — a plural group or a flat key as a whole
- [Extraction] **`{text}` in a module's call template writes the extracted text as a default value** (i18n Ally #1031): `t({key}, {text})` gives `t('greeting', 'Hello')`
- [Transloco] **`[translocoRead]` prefixes the keys of a `*transloco` block**, as `read:` does
- [Astro] **`t('key')` in `.astro` components** is supported once the Astro plugin is installed (i18n Ally #1063, #1347)

### Fixes

- [Stats] **A project with one message file per locale no longer shows a *translation (default)* namespace**: Paraglide's `messages/en.json`, next-intl or vue-i18n's `locales/en.json` read *Messages* in the Stats tab and in the table's namespace filter
- [YAML] **A value written into a YAML file reads back as written**: `Note: soon` no longer becomes a nested key, `Save # now` no longer loses ` # now` to a comment, and `yes`, `null` or `123` stay text. A key added to a mapping keeps its indentation

- [JSON] **A key added to a JSON file takes the file's own indentation, and sorting no longer reformats the whole file** (i18n Ally #1060, #755)
- [Paraglide] **`project.inlang/settings.json` is no longer read as a translation file**, and **a message file is no longer compared with itself**: no more `baseLocale` reported as an unused key, nor every value of the reference locale as *not translated?*
- [Paraglide] **An unknown message no longer mentions a `translation` namespace**: its tooltip says which message files were searched and what is missing, as Paraglide's files have no namespace
- [Navigation] **Ctrl+click on a key of a file named after its locale leads to its calls**: from `messages/fr.json` (Paraglide, next-intl, vue-i18n), *Go to Declaration* and *Find Usages* list `t('hello')` and `m.hello()` again, instead of nothing
- [JSON] **A root `$schema`, and the objects inside an array, are no longer read as keys**: no more `$schema` or `"countPlural=one"` in the tool window, the completion, the statistics or *Unused translation key*
- [Rename] **Renaming a key works on files a VCS keeps read-only**: the files are checked out first instead of failing halfway
- [Reviews] **With a single module configured, every view compares the same reference locale and reads the same `.i18n-reviews/` folder**
- [Stats] **With a single module configured, the Stats tab follows the module's reference locale** rather than the most translated one
- [Translation changes] ***Retranslate Lagging…* leaves out a module that translates from another locale** instead of proposing its source for retranslation
- [Extraction] **In a project without any translation file, *Extract I18n* writes the default value too**, as the extraction dialog does

## 1.10.0 - 2026-10-11

### Features

- [Extraction] **Internationalize a file or a folder in one go**: right-click files or folders in the Project view, or in the editor, and choose *Internationalize…*. Every hard-coded text of their JS/TS files and Vue components is found in the background, then previewed per file — a check box, an editable key, an existing key reused when it holds the same text — and *Apply* writes values, missing files, calls and `useTranslation` hooks in one command: a single Ctrl+Z undoes it all. In a `.vue` file, the `<template>` texts become `$t` calls (`:placeholder="$t('…')"`, `Hello {{ user.name }}!` → `Hello {name}!`), and the `<script>` strings become `t('…')` with `useI18n()` added to `<script setup>`, or `this.$t('…')` in the Options API. Strings that are code by their place (hook arguments, imports, `className`, `href`, `defineProps`…) are never offered; URLs, paths, colours, dates and numbers start unchecked, the reason shown. When machine translation is enabled, the new keys are also translated into the other locales and previewed before being written in the same command
- [Review] **Review translations in the tool window table**: in a module with a `.i18n-reviews/` folder, each locale cell shows its review — to review, approved, changes requested — and its tooltip who decided, when, where the value came from and the last comment. Right-click selected cells to *Approve*, *Request Changes…*, *Mark for Review* or open the *Comments…* thread; the *Status* filter adds *To review* and *Changes requested*. An approval holds for the value it was made on: change the value and the cell is to review again. Reviews are stored one file per locale (`.i18n-reviews/<locale>.json`) and signed with the name set in *Settings | Tools | i18n Support Plus | Reviews* — by default the Git user. *Fill Missing Translations…* and *Internationalize…* can mark the values they machine-translate as to review, with the engine they came from. Editing a key shows each locale's review under it, with a *Review…* link to its thread; a locale filled by *Translate* and confirmed as proposed is marked to review, one retouched by hand is not. Reviews follow their key: renaming it (a plural's forms or a whole level included) or moving it to another namespace moves its reviews, and the approval still holds; deleting it — the *Unused translation key* quick fix included — deletes them, one Ctrl+Z restoring both. *Tools | i18n | Clean Up Orphan Reviews…* lists and deletes, once confirmed, the reviews left without a value — never on its own, and never in a module whose translations load empty. A module without the folder sees no change
- [Laravel] **PHP translation files are read**: `lang/en/messages.php` — `return [...]` or `return array(...)`, nested arrays included — answers `__('messages.welcome')` and `trans('messages.auth.failed')`, the file name being the namespace. Navigation both ways, completion, unknown keys reported, *Create key* writes into every locale, and the tool window shows and edits them. Requires the PHP plugin
- [Laravel] **Package keys `vendor::file.key` are read**: `__('courier::messages.welcome')` — and `trans`, `trans_choice`, `@lang`, Blade echoes — resolves in the override `lang/vendor/courier/en/messages.php`, with navigation, completion (`courier::messages.`) and unknown keys reported. A package without override in the project, its translations registered at runtime from Composer's `vendor/`, is not read
- [Laravel] **A Laravel module preset**: *Laravel (PHP)* in the setup wizard and a module's *Preset* fills the layout Laravel documents — `lang/{lang}/{ns}.php`, keys `{ns}.{key}` — and the wizard ticks it when `composer.json` requires `laravel/framework`. `lang/en.json` keeps resolving; `resources/lang/` (before Laravel 9) needs its path template adjusted by hand
- [Translation] **A project glossary for machine translation**: *Machine Translation* settings take one term per line. `Acme Cloud` alone is never translated — masked like a variable for every engine, and a translation that loses it is refused. `cart = fr: panier; de: Warenkorb` is sent in the prompt of the OpenAI-compatible preset (`{glossary}` placeholder) and to DeepL as a glossary of its own, created per language pair and recreated if deleted; a refusal translates without it and says so. Saved in `.idea/i18nMachineTranslation.xml`
- [Translation] **Fill every locale at once**: *Fill Missing Translations…* offers *All locales* — one preview with a *Locale* column, one write, one Ctrl+Z. The preview also shows which engine translated each proposal, so a text sent off the machine after a fallback is never a surprise, and *Move Up* / *Move Down* reorder the engines
- [Editor] **Edit a translation from the code**: on `t('common:menu.home')`, *Edit Translation* (`Ctrl+Alt+Shift+I`, editor context menu) or the *Edit* link of the Ctrl+hover hint opens the translation dialog on that key, every locale filled in; a key no file holds yet opens it in creation mode
- [Editor] **An unresolved key says where it was looked up**: the tooltip tells how the key was read — its namespace and where it comes from, the module, the files looked up (`no file for namespace 'ghost' in module 'web'`), the segment missing (`'user' exists, 'name' does not`) — and offers to open the settings. A missing key and a wrong configuration no longer look the same
- [Editor] **A translation file shows the reference value of each key**: in `fr/common.json`, `"save": "Enregistrer"` reads `en: Save` as an inlay hint, or `missing in en`. JSON and YAML; toggled under *Editor | Inlay Hints* as *i18n reference values*
- [Extraction] **The default value can be written in the call**: a module's *Write the default value in the call* (off by default) turns `Save changes` into `t('save', 'Save changes')`, or `t('greeting', { defaultValue: 'Hello {{name}}', name })` — shown by i18next while the key has no translation. JavaScript files of an i18next module, or of a module without preset
- [Inspections] **Locales not checked for missing keys**: a locale in progress or abandoned (`de, pt-BR`) no longer fills the project with *missing key* warnings; it is still shown everywhere and machine translation can still fill it. `de` covers `de-DE` (#734 on i18n Ally)
- [CI] **Check translations in CI**: the inspections run without an editor, in Qodana or a headless IDE (`inspect.sh`), and report missing keys, unresolved keys and variables not passed — checked on the example project with Qodana for JS 2026.2. [docs/ci](docs/ci/README.md) holds a ready-to-copy `qodana.yaml`, a GitHub workflow and an inspection profile. Every inspection now has a description, shown in the settings and in the reports. Qodana for JS needs a Qodana Cloud token
- [Export] **Export only the missing translations**: *CSV, Missing Only* exports the keys at least one locale lacks or leaves empty, with all their values; re-importing it writes only the cells the translator filled
- [next-intl] **Server Components keep their namespace**: under `const t = await getTranslations('Home')` — or `getTranslations({ locale, namespace: 'Home' })` — `t('title')` resolves to `Home.title` like under `useTranslations('Home')`
- [Transloco] **The directive's `read` is read**: under `<ng-container *transloco="let t; read: 'admin'">`, `t('title')` is the key `admin.title`, in the scope `admin` when `i18n/admin/` holds one. The directive closest to the call decides
- [vue-i18n] **Linked messages are navigable and count as usages**: in `"Click @:common.save"` — or `@.lower:`, `@:{'…'}`, `@:(…)` — the linked key opens on Ctrl+click and shows in Find Usages, an unknown one is reported, and a key only linked is no longer reported as unused. JSON and YAML
- [vue-i18n] **`<i18n-t keypath>` and `v-t` complete and fold**: `<i18n-t keypath="common:user.<caret>">` offers the keys under `common:user` with their value, and folding replaces the key with its value. A bound `:keypath` holding a constant string (`:keypath="'terms.accept'"`) is read as a key too. react-i18next's `<Trans i18nKey="…">` gets the same prefix-aware completion
- [Updates] **What's New opens in the IDE**: the update notification's *What's New* button shows, in an editor tab, the notes of the installed version and of every version skipped since the last one announced, instead of the whole CHANGELOG on GitHub. *Help | What's New in i18n Support Plus* reopens them at any time. Without JCEF, the CHANGELOG still opens in the browser

### Bug Fixes

- [Inspections] **Unused translation key leaves configuration files alone**: in a headless run, every key of `package.json` and `tsconfig.json` was reported as unused. Only translation files are checked now
- [Settings] **The setup wizard ticks Laravel by itself**: it read only `package.json`; it now reads `composer.json` too, so a Laravel + Vue project gets both boxes ticked
- [Laravel] **Package overrides in `lang/vendor/` are read**: `vendor` was skipped as Composer's folder, which also hid `lang/vendor/<package>/`, even in JSON. Composer's `vendor/` and `node_modules` stay excluded
- [Translation] **DeepL and Google get the language codes they document**: DeepL gets `EN-US`, `PT-BR` or `ZH-HANT` as target (a region it lacks falls back to the language), Google `zh-CN`, `pt-BR`. A request body rewritten by hand keeps the labels as they are

## 1.3.1 - 2026-08-25

### Bug Fixes

- [Unused Key inspection] Stop underlining — and offering to delete — a key reached by a key built at runtime. The inspection is the third place that decides a key is dead, and the only one where the deletion is a single click with no preview in between. Both signals it reads come back empty on such a key: `t(`common:status.${kind}`)` writes no name to search for, and the reference it does carry resolves onto the property's *key literal*, which is not what `ReferencesSearch` on the property compares against. It now asks `DynamicKeyUsages`, like the scan does, with one cache of dynamic heads per file — the properties of a translation file share their prefixes almost entirely, so the search runs a handful of times rather than once per key on every keystroke. The key is composed on the spot rather than read from the element's own reference: the provider attaches one only when the key already occurs in the sources, which is by definition never true of the keys this inspection reports
- [Scan Orphans] Stop counting a call to a **neighbouring key**. The match was a prefix one with no boundary, so `menu.home` counted `menu.home-page` as one of its usages. Its reach was narrower than it looks — `processElementsWithWord` matches whole words, so `menu.homePage` never reached the filter to begin with, and only a separator that ends a word (`-`, the default plural separator) got through — but it inflated the count and could hide a genuinely dead key. Whatever follows the key must now open a new segment, or be nothing at all. The prefix match itself stays: a key naming an *object* is legitimately reached by every call under it, which is what makes navigation from a parent node find its children's call sites
- [Scan Orphans] Check the namespace a bare call site works under. The scan searches the bare form of a key so that `useTranslation('navigation') + t('menu.profile')` is found, but nothing verified *which* namespace the hook declared — so a `t('menu.profile')` written under `common` was counted as a usage of `navigation:menu.profile`, and of every other namespace holding a key by that name. The namespace written at the call site wins; with none written, the one its `useTranslation` declares is read through the same extraction annotation and completion go through. A call site declaring nothing at all still counts: reporting a live key as an orphan is the error worth avoiding
- [Scan Orphans] Stop calling a key **unused** when only a runtime-built key reaches it, and stop offering it for deletion. `t(`deposit-box:status.${x}`)` names none of the `status.*` keys, so the text scan finds nothing for any of them: the *Usage* column read *Unused*, and *Cleanup unused keys* — which takes its candidates from that very count — offered to delete keys that are in use. The action did carry a guard against exactly this, but it never fired: a template literal's reference resolves onto the JSON property's *key literal*, while `ReferencesSearch` on the property compares against the property itself, so the answer was always "no reference at all" — and the only test covering it asserted the negative case, which passes whatever the function returns. The guard is replaced by `DynamicKeyUsages`, which reads the static head of the dynamic literals the sources hold (`deposit-box:status.`) and treats every key under it as reachable. The rule is one of prefix, not of resolution: what the literal will hold is unknown until it runs, so a dead sibling is spared too — the side to err on when the alternative is deleting a live key. One search per distinct head, not per key, and only the rows the text scan left at zero are re-examined. The column carries a fourth state, *Dynamic*, distinct from *Unused* in wording, icon and colour, and *Delete orphan key* stays disabled on it
- [Scan Orphans] Stop reporting every **pluralized key as an orphan**. A key stored as `account:…addTrustee.description_other` is a *form*, not a key: the source code writes `t('account:…addTrustee.description', { count })` and i18next appends the suffix at lookup time. The scan searched the sources for the stored form, which by construction is never written there, so every `_one` / `_other` / `_zero` / `_two` / `_few` / `_many` row — and every legacy numeric form (`key-1`, `key-2`, `key-5`) — came back with zero usages. The consequence went past a wrong number in the *Usage* column: *Cleanup unused keys* takes its candidates from that same count, so it offered to delete translations that were in use. The suffix is now stripped before searching, through the rule `KeyComposer` already applied when composing a key for a reference — which is why Ctrl+click from the JSON file always worked while the scan did not. A key merely *ending* like a plural form (`step_one`) is stripped too: the two are indistinguishable without reading the sibling keys, and reporting a used key as used is the safe side of that ambiguity
- [Scan Orphans] Count a call site **once**, not once per search term. A key carrying a namespace is searched twice — prefixed (`navigation:menu.profile`) and bare (`menu.profile`), since the namespace may be implicit at the call site — and both searches accumulated into the same list without deduplication, so three real usages were reported as six. The count is now taken over distinct elements

### Documentation

- [Example project] Make `examples/react-multi-namespace` representative of a real i18next codebase rather than of the happy path. It held four flat namespaces, one call shape and no case the plugin could get wrong; the shapes now covered were read off a production project: a namespace carrying a dash (`deposit-box` — the plugin's default plural separator, in a namespace name), a six-level key path, CLDR plurals whose suffix is never written at the call site, a plural form sitting next to a plain key of the same name, markup in the value rendered through `<Trans>`, a multiline value, a key built at runtime as a template literal that nothing can resolve statically, and a key passed as an option of another key. ## 1.3.0 - 2026-08-23

### New Features

- [i18n] Localize the plugin itself, starting with the **tool window**, and ship a complete **French** translation. A plugin whose whole subject is internationalization exposed its own interface in English only: `I18nBundle.properties` held 75 keys against a `SettingsPanel` that used 65 of them, and everything else — tool window, wizard, dialogs, actions, notifications — was hard-coded. This batch covers the tool window's four panels: tabs, toolbar actions, the tree root, the table's columns, namespace filter, orphan scan and context menu, and the statistics panel. `PluginBundle` now extends `DynamicBundle` instead of `AbstractBundle`, which is what makes translation visible at all: `AbstractBundle` resolves against the JVM's default locale, so a translated file would only ever load on a machine whose JVM runs in that language, whereas `DynamicBundle` follows the locale the IDE itself runs in — the one a language pack changes. Strings are reached through `PluginBundle.message`, whose key carries `@PropertyKey`, so a key absent from the bundle is flagged in the editor rather than rendered as `!some.key!` in the interface. The remaining packages keep their hard-coded strings until their own batch; this one changes no behaviour and no English wording
- [Actions] Reach **Sync Keys** from the *Tools* menu. The synchronizer was called from exactly one place — the tool window's toolbar — and none of the eight declared actions covered it, so the feature was absent from *Tools > i18n Support Plus*, from *Find Action* and from any keymap assignment. That is the argument that had *Run Setup Wizard* added to the menu in the first place: a feature reachable from a single point of the interface is one half the users never find. It is now declared once, and the toolbar button resolves that same registered action instead of calling the synchronizer a second time, so both entry points carry the same label, icon and behaviour. No default keyboard shortcut is assigned — three are already taken (`ctrl alt shift T/B/M`) and a fourth by default would be intrusive
- [Display] Render **ICU MessageFormat** values instead of showing their source. react-intl / FormatJS pluralizes inside the value rather than through sub-keys, so folding replaced `t('cart.items')` with `{count, plural, one {# arti…` — strictly less readable than the key it hid, which emptied folding, hints and inlay hints of their purpose on every react-intl project. A representative branch is now displayed (`other`, falling back to the first one declared) with `#` replaced by its argument, so the same key reads `{count} articles`. `plural`, `select` and `selectordinal` are covered; this is a display layer, not an ICU engine — no argument value exists at that point, resolution and annotation are untouched, and a malformed message falls back to its raw value rather than throwing. Rendering happens before truncation, which used to cut in the middle of a brace, and a message without a single `{` — every i18next project — is returned unchanged without any scanning

- [Setup Wizard] Detect **react-intl / FormatJS** in `package.json` (`react-intl`, `@formatjs/intl`) and offer it alongside i18next, vue-i18n and lingui. The framework has been supported by the plugin for several releases but was invisible in the wizard, so a react-intl project looked unsupported on first launch. Matching is textual on the quoted dependency name, so `react-intl-universal` — a different library — is not mistaken for it
- [React-Intl] Extract the keys declared in a `defineMessages({ … })` / `defineMessage({ … })` catalogue. A react-intl project usually declares its messages apart from where they are used, then references them (`intl.formatMessage(messages.greeting)`); `ReactIntlExtractor` only ever saw the descriptor passed **inline** to `formatMessage`, so a project following the idiomatic layout had none of its ids annotated, completed or navigable. Both catalogue shapes are recognised — the descriptor as the call argument itself, and the usual one level below it (`{ greeting: { id } }`) — and only `id` is claimed: `defaultMessage` and `description` hold source text and are vetoed against the generic string-literal extractors, catalogue included. The indirect use site is deliberately left alone: resolving `messages.greeting` back to its declaration is a PSI reference resolution and a separate concern
- [i18n-js] Recognise **i18n-js**, the dominant i18n library of the React Native / Expo ecosystem, as a technology of its own. No technology declared it, and that such projects worked at all was an accident: `t` happens to be published by i18next, so an i18n-js project silently depended on a framework it does not use and would have broken had i18next been narrowed or disabled. `I18nJsTechnology` declares `t` and `i18n.t` — the qualified form has to be listed explicitly, since a qualified call whose full text is not a declared name is rejected, which is what keeps `toast.t('…')` out. Source discovery is left to `TsCatalogTechnology`, which already reads the locale-keyed TypeScript catalogues these projects use
- [Settings] Add **Treat keys as flat** (`flatKeys`, off by default) — resolves a key as a single property instead of splitting it on the key separator. react-intl / FormatJS projects store flat ids (`"app.header.title"` is one JSON property, not three nested levels), which the nested resolution could never match, making every key in such a project unresolvable. The setting reuses the parsing path gettext already relied on (`KeyParserBuilder.withoutTokenizer()` plus `emptyNamespace`), now shared through `Config.usesFlatKeys()`: namespace parsing is off too, so a `:` is just part of the key and translation files are located through the default namespace. Applied consistently to annotations, key extraction (single and batch) and the JS/JSX/PHP reference assistants. Existing projects are untouched — nested resolution stays the default
- [Frameworks] Recognise the idiomatic syntaxes of react-intl, ngx-translate and svelte-i18n. Their key extractors have existed since #52 but were never referenced by `JsLang` or `JsxLang`, so only the plain `fn('key')` form resolved through the generic extraction — `formatMessage({ id })`, `<FormattedMessage id>`, `translate.instant('key')` and the `| translate` pipe silently resolved to nothing. Extractors that own their syntax are now consulted before the `translationFunctionNames` filtering, which is what a descriptor object or a qualified call needs: the generic path matches only bare first arguments and rejects qualified calls by design. The ngx-translate pipe is reachable inside JSX/TSX only — the plugin registers no annotator for standalone Angular templates
- [Tool Window] Reload the tool window when the translation files change, instead of showing stale data until someone clicks *Refresh*. It is matched on the path, not on the file type, so a TypeScript catalogue — which no `Localization` declares a type for — is recognised like any other source; a file not displayed yet only counts on a structural change, which is what lets a newly created locale file get in

The dialog's *Add namespace* button keeps the tool window's keys rather than duplicating the wording: it is the same feature reached from a second place. ### Bug Fixes

- [Settings] Stop clipping the *Add* / *Remove* buttons and the field comments of the Modules and Rules editors. `ListEditorPanel` pinned the panel holding the item list and its two buttons to a fixed 200px and handed it to `BorderLayout.WEST`, which allocates a WEST child exactly its preferred width and never more — so the 238px the buttons actually need were cut, and *Remove module* reached the screen as "Remove m…". Both editors did the same thing one level up, pinning themselves to 700px for a form needing 785px, which is why the field comments were sliced off the right edge mid-sentence instead of scrolling: a panel that under-reports its preferred width does not get a scrollbar, it gets squeezed. Both widths are now measured from the content rather than chosen, which is what makes the fix hold: the button labels come from the bundle, so a constant that fits in English clips in a longer language, and the IDE renders in a font the build JVM does not have — the English headless measurement was not the worst case, and the rules editor proved it by fitting in the test while being visibly cut in the running IDE. The modules editor now measures itself after its form is populated, since the preset combo is built empty and only receives its items in `bind`. The two buttons also move from a gapless `BoxLayout` to a `FlowLayout` with margins, which is most of why they read as flat text rather than as a pair of controls. `ToolbarDecorator` — the platform idiom, and what would render them as the usual `+` / `−` pair — was weighed and declined: it needs a running Application, which would put these panels out of reach of the only tests that cover them, and those tests are what caught this. Four cases now assert both widths headlessly, the first thing in the suite to measure a rendered dimension
- [Navigation] Give every framework's translation calls the same navigation. `JsReferenceAssistant.pattern()` hardcoded `t` and `$t` instead of reading the names each `Technology` publishes, while annotation read the whole list — so a key passed to `$tc`, `$te`, `msg`, `i18n._`, `_` or `$_` was underlined as unresolved and yet had no reference at all: no Ctrl+click, no rename, no find-usages, on names the README announces as supported. The pattern is now built from the published names, matching on the method name so a qualified one (`i18n._`) still matches, with the qualifier checked as before — which is what keeps `toast.t('…')` and `toast.instant('…')` out. Nothing new is claimed: this aligns what is navigable with what was already being annotated
- [Show Translations Inline] Let the folding toggle be translated at all. It passed its text and description to `ToggleAction`'s constructor, and a literal set there wins over the label `plugin.xml` resolves from the bundle — so this one entry would have stayed English in a localized IDE while every other one followed the language. Text, description and icon now all come from `plugin.xml`, and a test asks the platform which of the two won
- [Cleanup Unused Keys] Fix *locale entrie(s)* in the summary shown after a cleanup — the plural was built by hand and lost its `s`
- [Settings] Show the plugin's name without its stray quotes in the settings tree. `app.name` was stored as `"i18n Support Plus"` — quotes included in the value — so the *Settings > Tools* entry read back with them, which no other node in that tree does
- [Display] Handle ICU **apostrophe quoting** and single-value formats in the message renderer. `'{'` and `'}'` are literal braces in ICU, but the renderer counted them as real ones, so a message mixing a quoted brace with a plural fell back to its raw ICU source — the exact case the renderer exists to avoid. Quoting now follows ICU's default rules: `''` is one apostrophe, a lone `'` quotes only before `{`, `}` or `#`, and stays a plain apostrophe everywhere else, which leaves French values such as `L'article` untouched. A quoted `'#'` inside a plural branch also stays literal instead of being substituted. **Behaviour change**: `{amount, number, currency}`, `{day, date, short}` and `{hour, time, short}` now display as `{amount}`, `{day}` and `{hour}` rather than showing the whole format declaration — no value exists at display time, so the format was noise
- [Hints] Escape translation values before they reach the Ctrl+hover popup. The popup is assembled as raw HTML and interpolated the value straight into a `<td>`, so any translation carrying markup (`Voir <b>les CGU</b>`), an entity (`&nbsp;`) or a comparison (`a < b`) was parsed as markup instead of being shown: text swallowed, styles leaking into the following rows. The locale label and the file path behind the navigation arrow went through the same path, and the path sits in a single-quoted attribute where one apostrophe was enough to close it. All three are now escaped with the platform's `StringUtil.escapeXmlEntities`. Escaping is applied last, after ICU rendering and truncation, so the 60-character budget still counts source characters rather than entities — and a translation without a special character comes out byte-for-byte as before
- [ngx-translate] Fix `NgxTranslateExtractor` reading the literal's direct parent as the call expression: an argument's parent is the argument list, so the check never passed and `translate.instant('key')` was never extracted. The bug had gone unnoticed because the extractor was not wired to anything
- [React-Intl] Fix the very same argument-list bug in `ReactIntlExtractor`, which #151 corrected for ngx-translate but not here: it walked `objectLiteral.parent` expecting the call expression, so `canExtract` never returned true and wiring the extractor changed nothing — `formatMessage({ id })` still resolved to nothing. The call is now located with `PsiTreeUtil`, and matching on the `formatMessage` suffix covers every calling style: bare `formatMessage(…)` from `useIntl()`, `intl.formatMessage(…)`, and `this.props.intl.formatMessage(…)` from `injectIntl`
- [React-Intl] Never treat `defaultMessage` as a translation key. Inside a message descriptor only `id` is one; the other properties hold source text. Claiming `id` through the syntax-owned extractors is not enough — the descriptor's remaining literals still reach the generic path, which matches any string of a first-argument object — so they are now explicitly vetoed
- [React-Intl] Drop `t` from `ReactIntlTechnology.translationFunctionNames()` — react-intl has no such function. It only duplicated the name already published by `I18NextTechnology` (all technologies are active at once), widening the false-positive surface for every project. No behaviour change for i18next users
- [TS catalogs] Discover a catalogue declared as a plain TypeScript/JavaScript object keyed by locale (`export const translations = { fr: {…}, en: {…} }`), the norm in React Native / Expo projects. No code path read that shape: `TsLocalization` declares no file type, so the generic scan never opens a `.ts` file, and the only reader of a TS catalogue is hardwired to the i18next shape (a `resources` property holding `translation`). Nothing was found, so **every** key of such a project was flagged as having no translation file at all — annotator, completion, folding, hints, inlay hints, references and the tool window were all dead. `TsCatalogTechnology` now contributes one source per locale, rooted on that locale's object so `t('dashboard.title')` resolves against `translations.fr.dashboard.title`. An object counts as a catalogue only when **all** its top-level keys are locale codes, validated by the shared ISO-backed rule rather than by shape — two-letter codes collide with plenty of English words (`is`, `no`, `to`, `it`) — and the i18next shape is left to its owner so nothing is discovered twice. Candidates are pre-filtered on the conventional folders and file names, since opening every `.ts` file of a project on each resolution is not an option; a catalogue kept elsewhere is reachable through "Translations root directory". The technology contributes sources only — translation function names stay the business of the framework technologies
- [Resolution] Resolve keys that carry no namespace against a "one file per locale" project (`locales/fr.json` + `locales/en.json`). Such a key requests no namespace, so `findSources` fell back to the default one — `translation` — which the localizations match against the *file name*: a project owning no `translation.json` resolved nothing at all and every one of its keys was reported as having no translation file, across the annotator, completion, folding, hints, inlay hints, references and quickfixes. `findAllSources` had always read that layout correctly through its locale heuristic; the fallback simply was not wired into `findSources`, and `I18nGutterIconProvider` was the single consumer that had worked around it locally — gutter icons worked where everything else failed. The fallback now lives in `findSources` itself, and stays confined to keys that requested no namespace: an explicit namespace matching no file (`t('common:user.name')` without `common.json`) keeps being reported as an unresolved namespace instead of quietly resolving against unrelated files. A project owning the default namespace is unaffected — the file named after it still wins. Note that creating a key in such a project now offers the locale files that exist rather than proposing to create a `translation.json` next to them
- [Setup Wizard] Write the translations root on a **flat layout**. The wizard derived it by reading the grand-parent of every file it found, which assumes a fixed `locales/<locale>/<ns>.json` depth: on `locales/fr.json` that grand-parent is null, every candidate was dropped and **nothing at all was written** — right after the summary announced "2 file(s) found" and offered an *Apply* button, so the user believed the plugin was configured. The root is now derived by stripping the locale levels below it and taking the longest common prefix of what remains, so `locales/fr.json`, `locales/en/common.json` and the GetText `locales/fr/LC_MESSAGES/messages.po` all land on `locales`, and `src/locales/en/ns.json` on `src/locales`. Locale segments are recognised through the shared ISO-backed rule, so a folder named `lang` or `intl` is never mistaken for one. When no common root can be derived, the summary now says so instead of promising a configuration it will not write, and the root it will store is displayed before *Apply*
- [Setup Wizard] Offer the frameworks shipped since #151 — **ngx-translate** (`@ngx-translate/core`), **svelte-i18n** (`svelte-i18n`) and **i18n-js** (`i18n-js`), the React Native / Expo default. They were supported by the plugin but had no checkbox, so those projects looked unsupported on first launch. `locale`, `lang` and `langs` join the scanned folder names as well: `locale/` is the GNU GetText and Django convention, `lang/` the Laravel and Nuxt one, and all of them were already recognised as catalogue folders elsewhere in the plugin
- [Plurals] Stop reporting a nested plural object as "Reference to object". i18n-js, ruby-i18n and vue-i18n pluralize into `{ one: '1 boîte', other: '%{count} boîtes' }`, where i18next uses the flat `key_one` suffixes the resolver expands — so `t('common.box')` resolved onto the object and every plural key of those frameworks was flagged. A node whose children are *all* CLDR plural categories (`zero`, `one`, `two`, `few`, `many`, `other`) is now treated as resolved. Requiring **every** child to be a category is what keeps ordinary objects out: a namespace holding a key named `other` stays a namespace as long as it holds anything else
- [Gutter] Align the gutter icons with the resolution rule. This provider was the only consumer that had worked around `findSources` finding nothing for a key without a namespace: it substituted the default namespaces, then fell back to the whole project scan — which is why gutter icons worked on a "one file per locale" project while everything else reported the key unresolved. #159 moved that fallback into `findSources`, confined to keys that request no namespace, and the local one then became *wider* than the shared rule rather than redundant: it fired for an explicit namespace matching no file too. On `t('common:user.name')` with no `common.json`, the gutter showed per-locale statuses computed against unrelated files while the annotator reported an unresolved namespace — two verdicts on one key. The provider now passes the key's namespaces through untouched and leaves the fallback to the service
- [Display] Show the value of a **nested plural key** instead of nothing. Since #162 a key resolving onto `{ one: '1 boîte', other: '%{count} boîtes' }` — how i18n-js, ruby-i18n and vue-i18n pluralize — is annotated as resolved rather than reported as a "Reference to object". But folding, hints and inlay hints each required a leaf, so such a key was declared resolved while displaying nothing at all: the user saw the plugin recognise the key and never show its value. The three now go through a single entry point that returns the branch standing for the group — `other`, falling back to the first category declared, the same choice ICU rendering makes, so both pluralization styles read alike. A value is shown, never a sub-tree: a branch that is itself an object displays nothing, as does an ordinary object. Leaf keys are untouched, and ICU rendering and truncation still apply after the branch is picked
- [Setup Wizard] Apply the settings the wizard deduced, not just the translations root. *Apply* wrote `translationsRoot` and nothing else, while the scan already implied several other settings — and the framework checkboxes fed **nothing but a sentence** in the summary: ticking "react-intl", reading that it was detected and clicking *Apply* left the project exactly as unresolvable as before, until the user found `flatKeys` on their own. `WizardSettingsDeducer` now infers the default namespace from the file names (a "one file per locale" project names them after locales, so nothing is inferred there), turns GetText mode on when `.po` / `.pot` files are found, sets **Treat keys as flat** when react-intl is ticked — the setting #154 added for exactly those projects — and picks the preferred format from the majority extension. Ties are broken on convention then alphabetically, never on the order the file system returned. Nothing is ever overwritten: each field is written only while it still holds its default, because the wizard opens on first launch but is not guaranteed to write first. The summary lists the settings that will actually be stored, so the checkboxes finally mean something
- [Tool Window] Stop reading a source folder as a locale. The ISO-backed locale rule #122 introduced lived in `LocalizationSourceService`, but three consumers — the gutter icon tooltip, the Ctrl+hover popup and the tool window's data loader — each kept a **private copy** of the shape-only regex it replaced, and so never received the correction. The first two only mislabel a tooltip; the loader does not: it read the parent directory as the locale whenever it merely looked like one, so with a translations root covering a source tree, `src/api/common.json` was loaded under the locale `api` — the exact symptom #122 was reported for, still alive in the tool window because the loader had its own rule. The three copies are gone and all three call the shared one. The order they try the file name and its parent in was also inconsistent (the gutter and the hint tried the stem first, the loader the parent first); it is now stem, then parent, then the stem again as the fallback, so a file under a folder that names no language is labelled by its own name rather than by that folder. Projects using real codes (`en/`, `fr/`, `de.json`) are unaffected — this narrows the rule, it does not widen it
- [Tool Window] Stop indexing every key twice on a "one file per locale" project. The namespace was taken to be the file stem, unconditionally: on `locales/en.json` + `locales/fr.json` that made `en` and `fr` two namespaces, neither of them the default one, so the same key was prefixed once per locale — `en:menu.home` holding the English value, `fr:menu.home` the French one, and each missing from the other locale. Every consumer of that data was wrong in the same way: keys listed in double in the Tree and Table views with half-empty rows, roughly 50% of translations reported missing by the stats on a fully translated project, the doubling carried into the CSV export and back in through the import, and *Sync Keys* offering to create the `en:*` keys inside `fr.json` (the mandatory preview kept it from writing silently, but the proposal was wrong). A file named after its locale now contributes no namespace at all, so its keys carry no prefix, and the decision is delegated to the same rule that reads the locale off that file — the two cannot drift apart. The multi-namespace layout (`en/common.json`, `en/auth.json`), which is what most projects use, is strictly unchanged
- [Dialogs] Anchor the "Add Namespace" prompt to the dialog it is opened from. `TranslationDialog` is a modal `DialogWrapper`, and the prompt behind its "+" button passed the project as parent, which anchors a dialog to the IDE frame — the frame the modal dialog sits above. The prompt could therefore open **behind** the dialog that raised it, with both windows unresponsive until the hidden one was found. It is now parented on the button, so the platform anchors it to that dialog's window. This is the only `Messages.*` call the plugin makes from inside a modal dialog; every other one is raised from an action or a tool window panel, where the project is the right parent
- [Tool Window] Open a read action before validating the cached translation scan. `LocalizationSourceService.cachedSources` checks the PSI (`tree.value().isValid`) to avoid handing out elements a reload has invalidated, but the tool window reaches it from a pooled thread holding no read action — `TreeViewPanel`, `TableViewPanel` and `TranslationStatsPanel` all do — so the platform logged `Read access is allowed from inside read-action only` as a **SEVERE naming the plugin**, once per tool window opening, and surfaced it in *Report Errors*. Beyond the noise it was a genuine race: reading PSI concurrently with a write is exactly the `PsiInvalidElementAccessException` that check exists to prevent. The read action is opened inside the service rather than at each call site, so a fifth caller cannot reintroduce it, and it stays narrow — the scan itself already runs its own read actions, and holding one across a full rescan would block writes longer than this check needs. The existing cache tests never caught it because they wrap every call in `ReadAction.compute`; the new case calls from a pooled thread deliberately, and fails without the fix
- [GetText] Extract keys into the function a GetText project actually calls. `PhpTranslationExtractor` hardcoded its call template to `t($it)` and matched `t` alone in `isExtracted`, so extracting on a GetText project wrote `t('key')` — a call its own tooling does not scan and that the plugin itself would not recognise afterwards, since `PhpLang` and `PhpReferenceAssistant` both read `Config.gettextAliases` to *recognise* those calls. Only writing them had been left behind. The extractor now reads the same setting: with **GetText mode** on it writes the first configured alias (`gettext` by default, `_` / `__` if configured) and recognises an already-extracted call under any of them; with it off, `t` stays exactly as before. Note that writing the key into the `.po` catalogue already worked — the entry lands as a `msgid` / `msgstr` pair, and the msgid is the whole key, since a GetText project resolves keys flat
- [Tool Window] Hold **one** read action across the whole translation load instead of one per source. `TranslationDataLoader.loadAllTranslations` opened its read action inside the loop over the sources, so a write could land between two locale files and invalidate the elements the next walk was about to read — the `PsiInvalidElementAccessException` the cache guard in `LocalizationSourceService` exists to prevent, reintroduced one step further down. Every consumer walks the same batch: the Tree and Table views, the stats, the CSV export and import, and *Sync Keys*. The read action stays exactly as wide as the work it replaces — the walk only reads PSI and is bounded by the number of locale files — and `discoverLocales` deliberately keeps none of its own: it reads the locale off the file path, never off the PSI, so no read action of its own is warranted there
- [GNU GetText] Honor **Extract sorted** when the extracted key goes into a `.po` catalogue. `JsonLocalization`, `TsContentGenerator` and `YamlLocalization` each place the new node against a sorted anchor; `PlainObjectContentGenerator` appended at the end of the document unconditionally, so a GetText user who ticked the box got nothing — the setting was silently inert for that format alone. The entry now lands before the first one whose msgid sorts after it, and still at the end when it sorts after them all. Three details the flat format forces: whole msgids are compared, since a GetText key is not a path split into segments; the catalogue header (`msgid ""`) is neither moved nor used as an anchor, being metadata rather than a translation; and the insertion point is the first non-blank character of the target entry, which keeps a `#:` comment attached to the entry it documents instead of stranding it above a new one. Appending is untouched, so a project that leaves the setting off writes exactly what it wrote before
- [GetText] Navigate from a msgid to the code that calls it. `PlainObjectReferenceAssistant` was a declared-but-inert stub — `alwaysFalse()` and `emptyList()` — the only one of its kind in the repo, so translation→code navigation, which JSON and YAML have had all along, did nothing on a PO catalogue. It now reads the msgid off the `ID_LINE` of a section and resolves it against the calls in the source, matching the whole key: a msgid the searched key is only a substring of is not a usage of it. The navigation is served by `PlainObjectGotoDeclarationHandler` rather than by a `psi.referenceContributor`: the platform injects contributed references only into a `ContributedReferenceHost`, and no element of the org.jetbrains.plugins.localization tree is one, so a contributor computes references the IDE then drops. Ctrl+click reaches every element and carries the same references. The PO header (`msgid ""`) carries no key and offers no navigation
- [Lingui] Number the expressions inside a `<Trans>` instead of copying their source. Lingui catalogues `<Trans>Hello {name}!</Trans>` under the msgid `Hello {0}!` — it numbers the expressions it extracts — while the plugin reproduced `Hello {name}!` verbatim, a key no catalogue contains, so every interpolated `<Trans>` of a Lingui project was reported unresolved. Braces are matched by nesting depth rather than on the first `}`, so an expression holding one (`{cart.items[0]}`, `{cond ? "{" : ""}`) counts as a single placeholder instead of being cut in the middle. Text carrying no `{` is returned untouched — a plain `<Trans>` keeps the msgid it had — and an unbalanced `{`, which means the file is mid-edit, is left as written rather than turned into a placeholder matching nothing
- [Svelte] Analyse `.svelte` single-file components. The README listed them as not analysed, and the reason turned out not to be missing support but a missing **parser**: Svelte is not bundled in IntelliJ Ultimate, and without its plugin a `.svelte` file is `PLAIN_TEXT` — one `PsiPlainTextImpl`, nothing to read. With the plugin present, the `<script>` block and the `{…}` expressions of the markup are ordinary JavaScript PSI, so every extension already registered for `language="JavaScript"` applies inside a component without knowing it: annotations, completion, folding, hints and references all work, and `$_('key')` resolves in a component exactly as in a `.ts` file. **No production code was needed** — the capability was there all along, unreachable for want of a parser and undocumented. The plugin is declared as a test dependency so the suite can prove it, and the README now states the requirement rather than the false limit
- [Tool Window] Translate `(default)` in the namespace combo, and stop letting a namespace collide with the filter's own labels. The combo mixed the two: `All namespaces` came from the bundle but doubled as the sentinel the filter compared with `==`, and `(default)` was a hardcoded literal — displayed untranslated next to a translated entry in a tool window #177 had set out to localize, and untranslatable precisely because translating it would have broken the comparison reading it back. It also collided from the other side: a project owning a namespace named `All namespaces` or `(default)` selected it and got every row, since the selection equalled the sentinel. `NamespaceFilter` (All / Default / Named) now separates what an entry *is* — the type — from the text shown for it, which nothing compares; the combo holds filters and a renderer draws their labels, so `(default)` is a bundle key like the rest, `(par défaut)` in French. The filtering moves to `TableViewModel` with six tests, where it had none
- [Angular] Recognise the `| translate` pipe in standalone Angular templates. Two things stood in the way, and neither was the parser: the Angular plugin is bundled, and a `.html` inside an Angular project already parses into proper PSI. First, those interpolations belong to the **`Angular2` dialect**, not to `JavaScript`, so extensions registered for JavaScript never saw them — `angularConfig.xml` now registers against `Angular2`, mirroring what `vueConfig.xml` does for Vue. Second, `NgxTranslatePipeExtractor` requires an `XmlText` or `XmlAttributeValue`, which is what the pipe looks like in **JSX**, where markup is inert text; in a real template the key arrives as a `JSLiteralExpression` under an interpolation, so that condition never held. `AngularTranslatePipeExtractor` reads it where it actually is, and `AngularCompositeKeyAnnotator` carries it — each annotator holds its `Lang` in its constructor, so registering the JS one against `Angular2` would have brought `JsLang` along and changed nothing. The pipe is matched on the surrounding text rather than through Angular PSI classes, so the plugin still loads when the optional Angular dependency is absent. A `.html` outside an Angular project stays plain HTML and is untouched
- [Setup Wizard] Fold the two wizard flags into one, and stop the suggestion from being silenced forever. `wizardDismissed` (set by *Don't show again*) and `setupWizardEnabled` (the settings checkbox) were unrelated: unticking then re-ticking the box never cleared `wizardDismissed`, so a user who dismissed the wizard and later re-enabled it saw nothing, with the checkbox stating the opposite of what happened. One flag remains, the checkbox is the only switch, and a workspace carrying the old `wizardDismissed = true` migrates to `setupWizardEnabled = false` on load, so nobody's choice is lost. `needsSetup` also required three cumulative conditions — no module, untouched default namespace, blank root — meaning a half-configured project, or one whose translations folder had since moved, was never offered the wizard again; with no empty state in the tool window either, only the *Tools* menu was left, which nobody looks for on a plugin that appears broken. It now also fires when the configuration resolves to nothing, once per project opening, and the rule moves out of the startup activity into `SetupNeedDetector` where it is covered for the untouched, partial, dead-root and disabled cases. The scan itself ran on the EDT from `scanTranslationFiles()` and walked the repository through `walkTopDown` while skipping only `node_modules` and `build`, with `collectAll` recursing without a depth limit once a folder was recognised — enough to freeze step 2 on a large repository. It now runs under `ProgressManager`, cancellable, skips `dist`, `out`, `target`, `vendor` and `coverage` as well, and is bounded in depth on both halves of the walk

### Performance

- [Scanning] Cache the project-wide translation scan (`LocalizationSourceService.findAllSources`) on the project, instead of re-querying the file index and rebuilding one element tree per translation file on every call. The annotator, completion, folding, inlay hints, gutter icons and the tool window all go through it, so a project with many locale files paid a full rescan on every highlighting pass.
