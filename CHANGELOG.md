# Changelog

## Unreleased

## 1.3.0 - 2026-08-23

### New Features

- [i18n] Localize the plugin itself, starting with the **tool window**, and ship a complete **French** translation. A plugin whose whole subject is internationalization exposed its own interface in English only: `I18nBundle.properties` held 75 keys against a `SettingsPanel` that used 65 of them, and everything else — tool window, wizard, dialogs, actions, notifications — was hard-coded. This batch covers the tool window's four panels: tabs, toolbar actions, the tree root, the table's columns, namespace filter, orphan scan and context menu, and the statistics panel. `PluginBundle` now extends `DynamicBundle` instead of `AbstractBundle`, which is what makes translation visible at all: `AbstractBundle` resolves against the JVM's default locale, so a translated file would only ever load on a machine whose JVM runs in that language, whereas `DynamicBundle` follows the locale the IDE itself runs in — the one a language pack changes. Strings are reached through `PluginBundle.message`, whose key carries `@PropertyKey`, so a key absent from the bundle is flagged in the editor rather than rendered as `!some.key!` in the interface. The remaining packages keep their hard-coded strings until their own batch; this one changes no behaviour and no English wording
- [Actions] Reach **Sync Keys** from the *Tools* menu. The synchronizer was called from exactly one place — the tool window's toolbar — and none of the eight declared actions covered it, so the feature was absent from *Tools > i18n Support Plus*, from *Find Action* and from any keymap assignment. That is the argument that had *Run Setup Wizard* added to the menu in the first place: a feature reachable from a single point of the interface is one half the users never find. It is now declared once, and the toolbar button resolves that same registered action instead of calling the synchronizer a second time, so both entry points carry the same label, icon and behaviour. No default keyboard shortcut is assigned — three are already taken (`ctrl alt shift T/B/M`) and a fourth by default would be intrusive
- [Display] Render **ICU MessageFormat** values instead of showing their source. react-intl / FormatJS pluralizes inside the value rather than through sub-keys, so folding replaced `t('cart.items')` with `{count, plural, one {# arti…` — strictly less readable than the key it hid, which emptied folding, hints and inlay hints of their purpose on every react-intl project. A representative branch is now displayed (`other`, falling back to the first one declared) with `#` replaced by its argument, so the same key reads `{count} articles`. `plural`, `select` and `selectordinal` are covered; this is a display layer, not an ICU engine — no argument value exists at that point, resolution and annotation are untouched, and a malformed message falls back to its raw value rather than throwing. Rendering happens before truncation, which used to cut in the middle of a brace, and a message without a single `{` — every i18next project — is returned unchanged without any scanning

- [Setup Wizard] Detect **react-intl / FormatJS** in `package.json` (`react-intl`, `@formatjs/intl`) and offer it alongside i18next, vue-i18n and lingui. The framework has been supported by the plugin for several releases but was invisible in the wizard, so a react-intl project looked unsupported on first launch. Matching is textual on the quoted dependency name, so `react-intl-universal` — a different library — is not mistaken for it
- [React-Intl] Extract the keys declared in a `defineMessages({ … })` / `defineMessage({ … })` catalogue. A react-intl project usually declares its messages apart from where they are used, then references them (`intl.formatMessage(messages.greeting)`); `ReactIntlExtractor` only ever saw the descriptor passed **inline** to `formatMessage`, so a project following the idiomatic layout had none of its ids annotated, completed or navigable. Both catalogue shapes are recognised — the descriptor as the call argument itself, and the usual one level below it (`{ greeting: { id } }`) — and only `id` is claimed: `defaultMessage` and `description` hold source text and are vetoed against the generic string-literal extractors, catalogue included. The indirect use site is deliberately left alone: resolving `messages.greeting` back to its declaration is a PSI reference resolution and a separate concern
- [i18n-js] Recognise **i18n-js**, the dominant i18n library of the React Native / Expo ecosystem, as a technology of its own. No technology declared it, and that such projects worked at all was an accident: `t` happens to be published by i18next, so an i18n-js project silently depended on a framework it does not use and would have broken had i18next been narrowed or disabled. `I18nJsTechnology` declares `t` and `i18n.t` — the qualified form has to be listed explicitly, since a qualified call whose full text is not a declared name is rejected, which is what keeps `toast.t('…')` out. Source discovery is left to `TsCatalogTechnology`, which already reads the locale-keyed TypeScript catalogues these projects use
- [Settings] Add **Treat keys as flat** (`flatKeys`, off by default) — resolves a key as a single property instead of splitting it on the key separator. react-intl / FormatJS projects store flat ids (`"app.header.title"` is one JSON property, not three nested levels), which the nested resolution could never match, making every key in such a project unresolvable. The setting reuses the parsing path gettext already relied on (`KeyParserBuilder.withoutTokenizer()` plus `emptyNamespace`), now shared through `Config.usesFlatKeys()`: namespace parsing is off too, so a `:` is just part of the key and translation files are located through the default namespace. Applied consistently to annotations, key extraction (single and batch) and the JS/JSX/PHP reference assistants. Existing projects are untouched — nested resolution stays the default
- [Frameworks] Recognise the idiomatic syntaxes of react-intl, ngx-translate and svelte-i18n. Their key extractors have existed since #52 but were never referenced by `JsLang` or `JsxLang`, so only the plain `fn('key')` form resolved through the generic extraction — `formatMessage({ id })`, `<FormattedMessage id>`, `translate.instant('key')` and the `| translate` pipe silently resolved to nothing. Extractors that own their syntax are now consulted before the `translationFunctionNames` filtering, which is what a descriptor object or a qualified call needs: the generic path matches only bare first arguments and rejects qualified calls by design. The ngx-translate pipe is reachable inside JSX/TSX only — the plugin registers no annotator for standalone Angular templates
- [Tool Window] Reload the tool window when the translation files change, instead of showing stale data until someone clicks *Refresh*. The plugin declared no listener at all, so editing `common.json` in the editor left the tree, the table and the statistics on the previous values with nothing saying they were out of date — the worst of both worlds, wrong data presented as current. The subscription is programmatic and bound to the tool window content, so it lives exactly as long as what it reloads. Three things stand between a change and a reload, because reloading re-reads the whole PSI tree of every translation file: the change has to concern a file the tool window actually displays, a burst of keystrokes is grouped into a single reload, and a hidden tool window is not reloaded at all — it is marked stale and catches up when shown again. The relevance rule answers from a snapshot of the paths the last reload displayed rather than scanning: asking the service would rescan the whole project on every keystroke, since editing a file invalidates that cache. It is matched on the path, not on the file type, so a TypeScript catalogue — which no `Localization` declares a type for — is recognised like any other source; a file not displayed yet only counts on a structural change, which is what lets a newly created locale file get in
- [i18n] Localize the **setup wizard**, its startup notification and the settings **diagnostics panel** — the second batch of the plugin's own translation, after the tool window. The wizard is the very first screen a new user sees, and it was entirely hard-coded: title, step headers, navigation buttons, the summary written before *Apply*, and the four settings it announces it will store. Same for the notification that offers to run it, and for the yellow panel at the top of the settings that reports a missing translations directory or an empty namespace. Twenty-eight strings move to `I18nBundle`, in English and in French; the HTML of the summary is built around the translated sentences rather than concatenated with them, so a translation is never asked to carry markup it did not write. No behaviour and no English wording changes
- [i18n] Localize the **translation dialogs** — the third batch of the plugin's own translation, after the tool window and the setup wizard. `TranslationDialog` is where a key is created or edited, and every word of it was hard-coded: both titles, the *Key* and *Namespace* labels, and the two validation messages that block *OK*. `BatchPlaceholderDialog`, which asks what to write into the locales a new key did not cover, was in the same state, including the three options it offers. The undo entry the save registers — *Update Translation*, read back from *Edit > Undo* — moves to the bundle as well, as the tool window's own commands did. The dialog's *Add namespace* button keeps the tool window's keys rather than duplicating the wording: it is the same feature reached from a second place. Fifteen strings, in English and in French; no behaviour and no English wording changes
- [i18n] Localize the **menu entries** — the nine actions and the *Tools* submenu, which were hard-coded as `text=` and `description=` attributes in `plugin.xml`. Those are the labels a user reads in *Tools → i18n Support Plus*, in the editor context menu, in *Find Action* and in the keymap, and no amount of bundle work on the Kotlin side reached them. They now go through the `<resource-bundle>` the plugin already declared, under the platform's own `action.<id>.text` convention. 19 strings, in English and in French
- [i18n] Localize the **CSV import/export and the unused-key cleanup** — the second half of the actions lot. These three actions talk to the user more than anything else in the plugin: a module chooser, a file chooser, progress steps, two mandatory preview dialogs with their tables, and a result summary that counts what was written. The messages the CSV parser raises move with them: they are thrown as `IllegalArgumentException` but the import action puts them in an error dialog verbatim, so they are interface text and not log text, and leaving them behind would have produced a French dialog with an English body. 51 strings, in English and in French
- [i18n] Localize the **key-manipulation actions** — *Sync Keys*, *Move i18n Key*, *Rename i18n Key*, *Batch Extract* and *Sort i18n Keys*, which closes the `ide/actions` package. That covers the sync preview and its table, the four dialogs the move walks through when a key lives in several namespaces or collides in the target one, the rename prompt, and the undo entries all five register. 28 strings, in English and in French
- [i18n] Localize the **inspections** — the five display names shown in *Settings → Editor → Inspections*, the warnings they report, and the *Delete unused key* quick fix. This closes the plugin's own translation: every user-visible string now goes through `I18nBundle`, in English and in French. The display names move to the platform's `key=` attribute on `<localInspection>`, and the three `getDisplayName()` overrides that duplicated them are gone — a literal returned there is the same shadowing trap the folding toggle had. 15 strings
- [Settings] Add a **reference locale** per module (`referenceLocale`). Nothing recorded which locale a module translates *from*, so every feature needing an origin — copying a value into the empty locales, comparing message variables — had to guess. The field is empty by default, meaning "this module does not decide", and falls back to `previewLocale`, then `foldingPreferredLanguage`, then `en`. A workspace persisted before the field existed simply does not carry the option, so `XmlSerializer` leaves the default in place and the module behaves exactly as before — covered by a migration test that serializes a `ModuleConfig`, strips the option from the XML and reads it back

### Refactoring

- [Setup Wizard] Hand the navigation back to the platform's `AbstractWizard`, and turn the summary into a form. The wizard hid the platform's own buttons behind `createActions() = emptyArray()` and replaced them with three hand-rolled `JButton`s of equal visual weight, so nothing said which one validated, Enter and Escape did not behave as they do in every other IntelliJ wizard, and *Skip* was at once a navigation button and the cancel button. The SDK gives one accented default button, a *Previous* that greys out on the first step, and a cancel that stays a cancel — relabelled *Configure later*, so leaving no longer disguises itself as a step. The summary was one concatenated HTML string: every value readable, none correctable, and fixing a root meant walking back through steps that never held it, since the root is derived rather than typed anywhere. It is now editable components — root, default namespace, preferred format and both separators sit in the field that will be stored — each carrying the evidence it was read from (*Read from locales/en/common.json*), and *Apply* writes what the form holds instead of re-running the deduction and overwriting the correction. Above all, a guessed root is no longer presented as a fact: `TranslationRootDetector` widens to the longest common prefix when catalogues disagree, so a monorepo holding `apps/web/locales` and `apps/api/locales` landed on `apps` — a folder holding far more than translations — announced in the same tone as a value read off disk. The widening is now stated in an `InlineBanner`, and one module per catalogue is offered instead, each pre-filled with the path template its own files actually follow rather than the generic `{lang}/{ns}.json`. Validation moved to where the fields are: a blank separator blocks *Apply* through `CommitStepException`, instead of being reported by the diagnostics panel once the damage is stored. What is deduced has not changed — `WizardPlan` and `WizardChoices` ask `WizardSettingsDeducer` for every value and only add the origin — and both are UI-free, like `FrameworkDetector` and `TranslationRootDetector` before them, because the dialog cannot be instantiated headlessly; 27 cases now cover rules the dialog used to hold and nothing tested
- [Tool Window] Stop encoding a key's status in the text colour alone. The tree renderer carried everything in `foreground` — `JBColor.RED` for missing, `JBColor.ORANGE` for empty — two fixed constants outside the colour scheme, which no custom theme and no colour-blind palette could touch, and which roughly 8% of men cannot tell apart: for them the tree was a flat list. Status is now redundant across three channels — an icon, a `✓ ! ✗` mark and a colour taken from `JBColor.namedColor` — with a per-locale badge (`EN✓ FR! DE✗`) on leaves and a `12/14 (86%)` completeness ratio on branches, so a hole is found without expanding the whole tree, plus a permanent legend and `setAccessibleStatusText` for screen readers. The computation moves into `TreeViewModel.describeTree`, a single bottom-up walk indexed by path: the renderer reads a map instead of rebuilding a subtree on every repaint, which the naive version would have made quadratic. Keyboard access catches up with the table's — Enter edits, F4 opens the file at the right offset, `TreeSpeedSearch` searches inside collapsed nodes, and the context menu matches
- [Tool Window] Take the statistics bar's colours from the IDE scheme. The progress bar picked its tint from three hand-written `JBColor(Color(…), Color(…))` — six invented RGB values outside the platform palette — and the 90%/50% thresholds were stated nowhere, leaving the percentage as the only other information. Four `JBColor.namedColor` entries replace them, the thresholds are declared once and shared between the renderer and a new legend, and the bar shrinks to a 3px rule under a percentage painted on bare background, so the figure stays readable in greyscale. The panel's own *Refresh* button — a duplicate of the toolbar action — is gone in favour of loading on display, which is what makes `toolwindow.stats.idle` ("click Refresh to load") meaningless enough to delete
- [Settings] Replace the hand-painted diagnostics banner with the platform's `InlineBanner`, and give each diagnostic something to click. The panel repainted a `JPanel` with `JBColor(0xFFF3CD, 0x5C4A00)` — two invented tints — and reported a missing directory without offering to fix it, leaving the user to find the field themselves. The checks move into `ConfigDiagnostics.inspect`, pure logic with no Swing and no VFS: the file system arrives through a `DirectoryProbe` interface, results come back as typed issues, and localization happens at render time — which is what makes them testable headlessly. Each module's own root is checked too and the offending module is named, since a path on its own does not say which row to go and fix
- [Settings] Replace the Modules and Rules tables with typed master-detail forms. Both were bare `JTable`s whose every cell was free text (`isCellEditable(…) = true`), so booleans were typed by hand and `toBooleanStrictOrNull() ?: false` silently turned `"True"`, `"vrai"` or `"1"` into `false`; a typo in the priority column meant priority zero via `toIntOrNull() ?: 0`; a broken path template was accepted and failed later, far from its cause; and *Add* inserted a blank row that said nothing about what each column expected. The form uses a combo for the framework, a folder chooser for the root, checkboxes for booleans and a spinner for the priority, and a *Resolution* block under the templates shows the file actually produced (`src/locales/{lang}/{ns}.json` → `src/locales/fr/common.json`) along with what was found. Template parsing and validation move into `ModuleTemplateResolver`, pure and tested; the `component.name == bundle label` convention that `SettingsPanelTest` relies on survives the split and is now locked down by its own test
- [Dialogs] Name the 40-character cut applied to the value previewed by *Copy from primary locale*. It was an inline `take(40)` with its own `if (length > 40)` a few characters later, so the two halves of one rule could drift apart; it is now a single `ellipsised()` over a named constant, which is also what let the option become one bundle string instead of four concatenated fragments
- [Setup Wizard] Move framework detection out of `SetupWizardDialog` into `FrameworkDetector`, a UI-free object holding the dependency table, the checkbox labels and the matching itself. `SetupWizardDialogTest` could not instantiate the dialog headlessly and so carried its **own copy** of the dependency table: the tests passed on the copy and would have kept passing had the real table been broken. They now exercise the shipped code, and the wizard builds its checkboxes from the same table instead of a hand-maintained second list
- [Setup Wizard] Move the translation file scan out of `SetupWizardDialog` into `TranslationFileScanner`, and the root deduction into `TranslationRootDetector`, both UI-free. `SetupWizardDialogTest` carried its **own copy** of the folder and extension tables — the same trap #155 removed from framework detection: the tests exercised the copy and would have kept passing had the shipped lists been broken. They now run the shipped scan
- [Dialogs] Open the last three raw Swing dialogs through the platform. Everything else in the plugin goes through `Messages.*`; `KeysSynchronizer` and `TranslationDialog` still called `JOptionPane` with a `null` parent, which is not only a style difference — a parentless `JOptionPane` does not know the IDE frame, so it can open **behind** it and ignores the modality the platform manages, and it paints in the default Swing look & feel instead of the user's IntelliJ theme. The two "Sync Keys" notices now pass the project as parent, and the namespace prompt validates through an `InputValidator` while the user types rather than accepting a name and rejecting it afterwards in a second dialog — the platform mechanism for this, and one dialog fewer to dismiss. Displayed texts are unchanged; only the vehicle is
- [Tool Window] Give the shell an empty state, one level of tabs and a single toolbar. `buildContent()` knew only two cases — one module or several — and built tabs in both, so an unconfigured project got a one-node *Translations* tree and a statistics panel inviting a click on *Refresh* that could change nothing, while `SetupWizardDialog` existed with no path leading to it. A third case now answers with what the plugin looked for and what it read, and two links out: run the wizard, or configure by hand. Past two modules the panel nested a Tree/Table/Statistics `JBTabbedPane` inside a per-module one — two rows of tabs eating the height of a ~300px docked panel, and the inner selection lost when switching module; the module becomes a toolbar selector, tabs stay one level deep and the chosen view survives the switch. The toolbar resolves the actions the table and statistics panels gave up, tolerating an id that is not registered yet so the shell never fails to build. Search is debounced ~150ms through an injectable runner — it used to rebuild the whole tree and refilter the table on every keystroke, on the EDT — and answers with a result count, so *no match* stops reading like *empty project*
- [Tool Window] Stop encoding the table's status in the cell background, and stop dividing the width equally. `TranslationCellRenderer` and `UsageCellRenderer` repeated the tree's defect: the tint was the only carrier, so a missing value, an empty one and a translated one were one state to anyone who cannot separate the hues. Each cell now pairs an icon with a word, and the usage cell holds its count rather than a rendered string — `NOT_SCANNED` is not `ORPHAN`, a distinction the `—` placeholder carried alone. `AUTO_RESIZE_ALL_COLUMNS` handed *Key* — the longest text, and the one being scanned — exactly the share of a locale column, which at six locales in a docked panel left nothing legible: the key column starts widest, locale columns are draggable and can be hidden one by one (never the last one, which would show no translation at all and explain nothing), and the table scrolls rather than crushing itself. *Scan orphan keys* leaves its home-made filter bar to become a registered `AnAction` the shell's toolbar hosts. The cell states, the visible-locale set and the column widths move into `TableViewModel`, where they are tested without a Swing component
- [Dialogs] Label the translation fields by locale and validate while typing. Each text area was titled with `source.displayPath`, a raw file path — the locale, the one thing being looked for, appeared nowhere — and the layout stacked `BoxLayout` around `Dimension(520, 300)` and `Dimension(480, 80)` written in pixels, which a HiDPI screen truncated. The dialog is rebuilt in the Kotlin UI DSL with the locale as the row title and the path demoted to a caption. `doValidate()` only ever checked that the key was non-empty, so overwriting an existing key drew no warning and the project's separator was recalled nowhere: the key is now checked as it is typed — available, already taken, invalid segment — under the field. A *Copy to empty locales* button fills the blanks from the module's reference locale, or from the fullest one when no module declares one, and message variables (`{{count}}`, `{name}`, `%s`) are highlighted and compared across locales, so a translation that drops one is announced instead of saved in silence. The key check, the variable reading and the donor-locale choice are pure rules in `DialogViewModel`, each pinned by a test

### Bug Fixes

- [Settings] Stop clipping the *Add* / *Remove* buttons and the field comments of the Modules and Rules editors. `ListEditorPanel` pinned the panel holding the item list and its two buttons to a fixed 200px and handed it to `BorderLayout.WEST`, which allocates a WEST child exactly its preferred width and never more — so the 238px the buttons actually need were cut, and *Remove module* reached the screen as "Remove m…". Both editors did the same thing one level up, pinning themselves to 700px for a form needing 785px, which is why the field comments were sliced off the right edge mid-sentence instead of scrolling: a panel that under-reports its preferred width does not get a scrollbar, it gets squeezed. Both widths are now measured from the content rather than chosen, which is what makes the fix hold: the button labels come from the bundle, so a constant that fits in English clips in a longer language, and the IDE renders in a font the build JVM does not have — the English headless measurement was not the worst case, and the rules editor proved it by fitting in the test while being visibly cut in the running IDE. The modules editor now measures itself after its form is populated, since the preset combo is built empty and only receives its items in `bind`. The two buttons also move from a gapless `BoxLayout` to a `FlowLayout` with margins, which is most of why they read as flat text rather than as a pair of controls. `ToolbarDecorator` — the platform idiom, and what would render them as the usual `+` / `−` pair — was weighed and declined: it needs a running Application, which would put these panels out of reach of the only tests that cover them, and those tests are what caught this. Four cases now assert both widths headlessly, the first thing in the suite to measure a rendered dimension
- [Navigation] Give every framework's translation calls the same navigation. `JsReferenceAssistant.pattern()` hardcoded `t` and `$t` instead of reading the names each `Technology` publishes, while annotation read the whole list — so a key passed to `$tc`, `$te`, `msg`, `i18n._`, `_` or `$_` was underlined as unresolved and yet had no reference at all: no Ctrl+click, no rename, no find-usages, on names the README announces as supported. The pattern is now built from the published names, matching on the method name so a qualified one (`i18n._`) still matches, with the qualifier checked as before — which is what keeps `toast.t('…')` and `toast.instant('…')` out. Nothing new is claimed: this aligns what is navigable with what was already being annotated
- [Show Translations Inline] Let the folding toggle be translated at all. It passed its text and description to `ToggleAction`'s constructor, and a literal set there wins over the label `plugin.xml` resolves from the bundle — so this one entry would have stayed English in a localized IDE while every other one followed the language. Text, description and icon now all come from `plugin.xml`, and a test asks the platform which of the two won
- [Cleanup Unused Keys] Fix *locale entrie(s)* in the summary shown after a cleanup — the plural was built by hand and lost its `s`
- [Settings] Show the plugin's name without its stray quotes in the settings tree. `app.name` was stored as `"i18n Support Plus"` — quotes included in the value — so the *Settings > Tools* entry read back with them, which no other node in that tree does
- [Display] Handle ICU **apostrophe quoting** and single-value formats in the message renderer. `'{'` and `'}'` are literal braces in ICU, but the renderer counted them as real ones, so a message mixing a quoted brace with a plural fell back to its raw ICU source — the exact case the renderer exists to avoid. Quoting now follows ICU's default rules: `''` is one apostrophe, a lone `'` quotes only before `{`, `}` or `#`, and stays a plain apostrophe everywhere else, which leaves French values such as `L'article` untouched. A quoted `'#'` inside a plural branch also stays literal instead of being substituted. **Behaviour change**: `{amount, number, currency}`, `{day, date, short}` and `{hour, time, short}` now display as `{amount}`, `{day}` and `{hour}` rather than showing the whole format declaration — no value exists at display time, so the format was noise
- [Hints] Escape translation values before they reach the Ctrl+hover popup. The popup is assembled as raw HTML and interpolated the value straight into a `<td>`, so any translation carrying markup (`Voir <b>les CGU</b>`), an entity (`&nbsp;`) or a comparison (`a < b`) was parsed as markup instead of being shown: text swallowed, styles leaking into the following rows. The locale label and the file path behind the navigation arrow went through the same path, and the path sits in a single-quoted attribute where one apostrophe was enough to close it. All three are now escaped with the platform's `StringUtil.escapeXmlEntities`. Escaping is applied last, after ICU rendering and truncation, so the 60-character budget still counts source characters rather than entities — and a translation without a special character comes out byte-for-byte as before
- [ngx-translate] Fix `NgxTranslateExtractor` reading the literal's direct parent as the call expression: an argument's parent is the argument list, so the check never passed and `translate.instant('key')` was never extracted. The bug had gone unnoticed because the extractor was not wired to anything
- [React-Intl] Fix the very same argument-list bug in `ReactIntlExtractor`, which #151 corrected for ngx-translate but not here: it walked `objectLiteral.parent` expecting the call expression, so `canExtract` never returned true and wiring the extractor changed nothing — `formatMessage({ id })` still resolved to nothing. The call is now located with `PsiTreeUtil`, and matching on the `formatMessage` suffix covers every calling style: bare `formatMessage(…)` from `useIntl()`, `intl.formatMessage(…)`, and `this.props.intl.formatMessage(…)` from `injectIntl`
- [React-Intl] Never treat `defaultMessage` as a translation key. Inside a message descriptor only `id` is one; the other properties hold source text. Claiming `id` through the syntax-owned extractors is not enough — the descriptor's remaining literals still reach the generic path, which matches any string of a first-argument object — so they are now explicitly vetoed
- [React-Intl] Drop `t` from `ReactIntlTechnology.translationFunctionNames()` — react-intl has no such function. It only duplicated the name already published by `I18NextTechnology` (all technologies are active at once), widening the false-positive surface for every project. No behaviour change for i18next users
- [TS catalogs] Discover a catalogue declared as a plain TypeScript/JavaScript object keyed by locale (`export const translations = { fr: {…}, en: {…} }`), the norm in React Native / Expo projects. No code path read that shape: `TsLocalization` declares no file type, so the generic scan never opens a `.ts` file, and the only reader of a TS catalogue is hardwired to the i18next shape (a `resources` property holding `translation`). Nothing was found, so **every** key of such a project was flagged as having no translation file at all — annotator, completion, folding, hints, inlay hints, references and the tool window were all dead. `TsCatalogTechnology` now contributes one source per locale, rooted on that locale's object so `t('dashboard.title')` resolves against `translations.fr.dashboard.title`. An object counts as a catalogue only when **all** its top-level keys are locale codes, validated by the shared ISO-backed rule rather than by shape — two-letter codes collide with plenty of English words (`is`, `no`, `to`, `it`) — and the i18next shape is left to its owner so nothing is discovered twice. Candidates are pre-filtered on the conventional folders and file names, since opening every `.ts` file of a project on each resolution is not an option; a catalogue kept elsewhere is reachable through "Translations root directory". The technology contributes sources only — translation function names stay the business of the framework technologies
- [Resolution] Resolve keys that carry no namespace against a "one file per locale" project (`locales/fr.json` + `locales/en.json`). Such a key requests no namespace, so `findSources` fell back to the default one — `translation` — which the localizations match against the *file name*: a project owning no `translation.json` resolved nothing at all and every one of its keys was reported as having no translation file, across the annotator, completion, folding, hints, inlay hints, references and quickfixes. `findAllSources` had always read that layout correctly through its locale heuristic; the fallback simply was not wired into `findSources`, and `I18nGutterIconProvider` was the single consumer that had worked around it locally — gutter icons worked where everything else failed. The fallback now lives in `findSources` itself, and stays confined to keys that requested no namespace: an explicit namespace matching no file (`t('common:user.name')` without `common.json`) keeps being reported as an unresolved namespace instead of quietly resolving against unrelated files. A project owning the default namespace is unaffected — the file named after it still wins. Note that creating a key in such a project now offers the locale files that exist rather than proposing to create a `translation.json` next to them
- [Setup Wizard] Write the translations root on a **flat layout**. - [Action] Add **Move i18n Key to Namespace** action (`Ctrl+Alt+Shift+M` / editor popup) — moves an i18n key from its current namespace to another namespace atomically: copies the value to the sibling target file in every locale (creating the target file when missing, so no locale is silently dropped), deletes the source entry, and rewrites all code references with an explicit `targetNs:` prefix. The source namespace is derived from the *resolved* translation files, so keys whose namespace comes from a `useTranslation('ns')` or `useTranslation(['a','b'])` hook (no explicit prefix in the literal) are handled too. When the key resolves in several namespaces of a multi-namespace hook, the action first asks which namespace to move from. Code references are only rewritten when the literal actually carries the moved key (bare or `<ns>:`-prefixed), so an unexpectedly broad host element is never overwritten. If the key already exists in the target namespace, a confirmation dialog is shown before overwriting. The entire operation runs under a single `WriteCommandAction` (one undo step)
- [Inspection] Add **Empty translation value** inspection — flags leaf translation entries (JSON/YAML) whose value is empty or blank, closing the loop with `KeysSynchronizer`/CreateMissingKeys, which intentionally insert missing keys with an empty value. Object/mapping-valued keys are skipped. Disabled by default to avoid noise during work-in-progress translation
- [Inspection] Add **Duplicate translation value** inspection — flags leaf entries (JSON/YAML) that share the same non-blank value within a single locale file, helping translators spot copy-paste mistakes and keys that should be merged. File-scoped (same value across locale files is expected and never flagged); blank values are left to the empty-value inspection. Disabled by default
- [Action] Add **Sort i18n Keys Alphabetically** action (editor popup) — reorders the keys of the current JSON translation file alphabetically (case-insensitive), recursively into nested objects. Conservative: each entry keeps its own value text and the file is reformatted afterwards. YAML is out of scope for now (block indentation requires a separate safe-reorder strategy)
- [Settings] Wire up the previously inert **Sort keys alphabetically** setting — when enabled, every key creation in a JSON translation file (extract, quick fix, synchronizer) re-sorts the whole file so the new key lands in order even if the file was not already sorted. Sort logic is shared with the Sort i18n Keys action (`JsonKeySorter`). JSON only for now
